### Refactor 08 — ICollection on entity navigation collections

#### Overview

An EF entity's collection navigation should be declared `ICollection<T>`: EF Core needs to add to and remove from it, and `IEnumerable<T>` exposes no such API. Five collection navigations exist across `backend/StudentPortal/Models/Entities/`, and they disagree:

| Navigation | Declared type | Location |
|---|---|---|
| `Grade.Appeals` | `ICollection<Appeal>` | `Models/Entities/Grade.cs:38` |
| `Escalation.Assignments` | `ICollection<EscalationAssignment>` | `Models/Entities/Escalation.cs:19` |
| `User.Enrollments` | `IEnumerable<Enrollment>` | `Models/Entities/User.cs:27` |
| `User.Subjects` | `IEnumerable<Subject>` | `Models/Entities/User.cs:29` |
| `Subject.Enrollments` | `IEnumerable<Enrollment>` | `Models/Entities/Subject.cs:23` |

Two of five follow the convention and three do not. That is the whole campaign: three declared types, no behaviour change, no new test.

The change is compile-safe by construction. `ICollection<T>` derives from `IEnumerable<T>`, so every existing **read** of these properties still compiles — including `u.Subjects.Any(s => s.SubjectCode == subjectCode)` inside the expression tree in `UserRepository.GetProfessorsBySubjectCodeAsync`, which EF translates identically (and for which `ICollection` is in fact the shape EF expects). The only code that could break is an assignment of a bare `IEnumerable<T>` into one of the three properties; all three initialise with `new List<…>()`, which satisfies `ICollection<T>`, so there is nothing to fix.

**The target structure is defined in `Tech-Backend.md` §1** (`Models/Entities/` holds the EF entity classes). This is a type-declaration change only — the directory tree does not move, so no layout block needs refreshing and this campaign has no `Docs` subtask.

**Depends on:** nothing · **Blocks:** nothing

#### Out of scope

- **`IEnumerable<T>` return types on services, repositories and interfaces.** Those are read-only query results, where `IEnumerable<T>` is the correct and deliberate choice because the caller must not mutate them. Do not touch a single one. This campaign changes **only** the three entity properties in the table above.
- **The `= new List<…>()` initialisers.** They stay exactly as they are on all three properties.
- **`virtual`.** All five navigations are already `virtual`; that is unrelated to this change and does not move.
- **Reference navigations** (`Subject.Professor`, `Grade.Enrollment`, `Enrollment.Student`, and the rest). They are single references, not collections, and `ICollection` has nothing to do with them.
- **Any schema change.** A navigation's declared type lives only in the C# model. If `dotnet ef migrations add` would produce a non-empty migration after this change, something else moved — stop and find out what.
- **Entity nullability annotations.** `backend/StudentPortal.Tests` already emits `CS8632` warnings on `EscalationServiceTests.cs`; cleaning those up is separate work and must not ride along here.

#### Rollback

One subtask, one commit, three lines. If either suite goes red, `git revert` it — a red suite here means something depended on the weaker type, which is exactly what the gate is for, and the finding belongs in the box below rather than in a workaround.
